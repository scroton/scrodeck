# Parity: the native Windows shell against the Electron renderer

One row per feature of the Electron deck's window, grouped by the file that implements it. The specification
is `renderer/index.html`, `renderer/style.css`, `renderer/js/*.js`, `renderer/desk/bridge.js` (what a REMOTE
desk may do) and `lib/platform.js` (window keys). In REMOTE mode the native shell is a remote desk, so where the
browser desk and the Electron window differ, the browser desk (`bridge.js`) is the model. In LOCAL mode (`--local`)
it is the deck's own window, and the Electron window is the model; the rows that differ by mode say so, and
"Local mode" at the end lists what the local deck itself does not do yet.

Status: **done** = same behaviour and look, checked from a picture or a scripted run; **partial** = works, with
the stated gap; **missing** = not there (the reason says why).

How each row was checked: `windows/test/build-sidebar.ps1 -Truth` renders the real css + scripts in headless
Edge and compares pixel for pixel (the "px" figures below are strongly differing pixels on a 340 px wide
shot); `windows/test/shot.ps1 -Do "<script>"` drives the exe itself against the scratch deck through the same
handlers the window messages call (`windows/src/script.hpp`). `windows/test/shell.ps1` is the local deck's own suite (163 checks, temp folders only). Last full run of every suite: 2026-11-19; before that 2026-11-18 (the cloud panes, the cloud
dialog, the animations, the fonts: the same night, against the fake deck of `windows/web-test`, never a real site).

## A second window ("Open in a new window", "New … session in a new window", a tile dragged out)

**LOCAL mode: built (2026-11-19).** The core deck is multi-client, so a second top-level window of the process is a
second client of the same deck (`Deck::openWindow` / `addWindow` / `removeClient`; `src/deckhost.hpp`). Each window is
an `App` of its own (its view, target, scene, panes, web views); the D2D / DirectWrite / WIC factories and the bundled
fonts are the process's (`Gfx::initShared`), `config.json` is one, and a message-only hub window carries what
outlives any one window (the deck's wake-ups and timer, a clicked toast, a second launch).

**REMOTE mode: built (2026-11-19).** The deck lets in ONE remote desk at a time, so the other windows SHARE the first
window's socket (`Shell::remoteOwner`; `App::shareSend` / `shareReceive` / `shareLeave`): calls carry a rid unique across
the windows and each answer goes back to the window that asked; an attach is always sent (the deck answers it with the
replay) and the replay goes only to the window that attached; a detach goes out only when no other window still holds
the tile; `shown` is the union of the windows' sets (minimised only when all are); a resize goes from the focused
window, or when no other window holds the tile. The tile leaves the window it came from (one home per tile among this
machine's windows). Closing the first window closes the others (the socket is its); a reconnect reloads them all, each
keeping its layout. A remote's other windows are not kept across a restart (only the first window's layout is).
Checked: `windows/test/remote-window.txt` (via `windows/test/asks.ps1 -Script ... -NoAsks`): the new window's replay
and live output, the source window letting go, the window leaving.

## What a test must never do

`App::call` refuses these from a headless run and writes `BLOCKED <fn> <args>` to the run's log instead:
`adoptSession`, `moveAll`, `moveTile`, `restartNow`, `restartWhenQuiet`, `updateLater`, `saveAccounts`,
`saveSettings`, `askDone`, `askClear`, and `newTile` for anything but a shell (so `newTile({ kind: 'cloud' … })`, the
cloud dialog's Start, is never sent: no test makes a cloud session).

A test never loads claude.ai and never opens a browser: a cloud pane's web view is only made in a test when
`--cloud-base http://127.0.0.1:<port>` names a local stand-in (loopback only; `cloud.hpp`), every other address is
refused there, and what would have gone to the default browser is logged as `OPEN <url>`. A test's cloud profile is
`<--state-dir>\\web-cloud`, never the real one.

A test run also never touches the real clipboard: it copies to and pastes from a string of its own (`edit.hpp`
`testClipboard`; `dump clipboard`, `clip <text>`). Other sessions on this box use the clipboard.

That holds for every test run (`--shot`, `--window-shot`, `--bench`). A headless LOCAL run is a throwaway deck in a
temp folder (`--state-dir`), where saving settings or renaming tiles touches nothing else; what stays blocked there is
everything that could reach a Claude session or the user's accounts whatever `--allow-claude` says: `newTile` for
anything but a shell, `adoptSession`, `moveTile`, `moveAll`, `saveAccounts`, and `wakeTile` / `restartTile` /
`refreshTile` on a tile that is not a shell. A test's notifier only records (no toast, no flash, no shortcut), its
listener binds 127.0.0.1:8811-8819 or refuses, `tailscale` is never run, a restart starts nothing unless the test's
own `relaunch.json` names this very exe, and `--home <folder>` gives the deck a home that is not the user's. A test
run without `--state-dir` that would need the real `%APPDATA%\claude-deck-native` exits with code 7 before touching it.
